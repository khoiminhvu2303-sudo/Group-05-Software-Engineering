# 2.5 Relational data model
**2.5.1. Fundamental Concepts of the Relational Data Model**
The Relational Data Model represents real-world data as a collection of two-dimensional tables linked together through logical relationships.
In the context of a Library Management System, the core components of the relational model include:
•	Relation (Table): A structured format of rows and columns storing specific data. Each table represents a distinct business entity within the library, such as Books (Book), Members (Reader), Borrow Transactions (BorrowSlip), or Library Personnel (Staff) .
•	Tuple (Row / Record): Represents a single, specific instance of an entity. For instance, each row in the Reader table contains the complete profile of one individual library member.
•	Attribute (Column): Represents a specific property or characteristic of an entity. For example, Title, Author, and PublishYear are attributes defining the Book entity.
•	Domain: The set of permissible, valid values for a given attribute. For example, the Status attribute in a borrow transaction may only accept values within the domain {'Borrowed', 'Returned', 'Overdue'}.
**2.5.2. Keys and Data Integrity**

To uniquely identify entries and maintain consistent links across different library operations, the relational model relies on strict key constraints:
1.	Primary Key (PK):
o	An attribute (or set of attributes) that uniquely identifies each record in a table.
o	Enforces the Entity Integrity Rule: Primary key values must be unique and cannot be null (NOT NULL).
o	Example: ReaderID uniquely identifies a library member, StaffID uniquely identifies a library staff member, and BookID uniquely identifies a specific book.
2.	Foreign Key (FK):
o	An attribute in one table (child table) that references the Primary Key of another table (parent table).
o	Enforces the Referential Integrity Rule: Every value in a foreign key column must exist in the referenced primary key column of the parent table.
o	Example: The ReaderID field in the BorrowSlip table acts as a foreign key referencing ReaderID in the Reader table, preventing borrowing records from being issued to non-existent library members.
**2.5.3. Mapping Real-World Relationships to the Database**
  	
In designing the relational schema for the Library Management System, business interactions are mapped into three standard relationship types:
•	One-to-One (1:1):
o	Description: A record in Table A is associated with at most one record in Table B, and vice versa.
o	Application: The relationship between Staff and Account. Each staff member is assigned exactly one user account, and each account belongs to a single librarian.
•	One-to-Many (1:M):
o	Description: A record in Table A can relate to multiple records in Table B, but a record in Table B relates to only one record in Table A.
o	Application: The relationship between Reader and BorrowSlip. A single member can create multiple borrow requests over time (1), but each BorrowSlip is issued to only one specific member (N).
•	Many-to-Many (M:M):
o	Description: A record in Table A can relate to multiple records in Table B, and vice versa.
o	Application: The relationship between BorrowSlip and Book. A single transaction (BorrowSlip) can include multiple books, while the same Book title can appear on different borrow slips over time.
o	Implementation: Relational databases do not support direct N:M joins. This is resolved by breaking it down into two 1:N relationships using a junction table named BorrowDetail, which holds BorrowSlipID and BookID as foreign keys.
